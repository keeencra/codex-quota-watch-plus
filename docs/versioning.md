# 版本号与发布规则

生效日期：2026-09-13。根据所有者最新要求，采用 `v主版本.次版本.修订号`，仅重大升级增加第一位。此规则取代此前“新增功能就升主版本、中间位固定为 0”的约定；历史有效版本和原始下载包不变，生效时版本为 **v3.0.0、第 11 次有效迭代**；当前发布版本见 [VERSION](../VERSION)。

## 如何分级

| 类型 | 判断标准 | 编号示例 |
| --- | --- | --- |
| 大更新（主版本） | 达到下文的重大升级门槛 | `v3.4.2 → v4.0.0` |
| 小更新（次版本） | 在现有产品基础上增加兼容功能，或主动改善局部界面、交互、工作流 | `v3.0.2 → v3.1.0` |
| Bug 修复（修订号） | 修复已有缺陷、恢复预期行为；兼容性、安全或性能修复不引入新的功能范围 | `v3.1.0 → v3.1.1` |
| 文档与维护 | 仅修改日志、README、配图、宣传材料、维护规则，或仅做不改变产品行为的内部重构、测试、构建检查 | 版本不变 |

提高某一位时，仅将其右侧归零；数字可超过 9，例如 `v3.9.2 → v3.10.0`、`v3.1.9 → v3.1.10`，不得因数字达到 9 或累计多次小更新而进位成大更新。

## 大更新门槛

只有以下任一类**已完成并可验证的产品变化**，才考虑提高主版本：

1. **必要的不兼容升级**：公开接口、配对协议、配置或存储格式发生不兼容变化，现有用户必须迁移数据、修改配置或协调升级才能继续正常使用。仅重新构建、常规续签安装或内部重构不算。
2. **产品主要使用方式发生实质变化**：例如新增一种能够独立完成核心工作的新平台／运行方式，或显著扩展核心任务控制能力，形成新的完整使用流程。不能仅凭多一个页面、一个入口或一个服务接入来认定。
3. **完成整体产品体验的重大改版**：围绕明确目标，系统性改变多个核心流程，而非外观翻新或把若干零散小功能打包。应能清楚说明相比上一主版本，用户能完成什么以前无法完成的核心事情。

满足候选条件后，维护者仍须评估实际影响并在更新日志写出“为什么需要主版本升级”。不以改动文件数、代码行数、提交次数、累计 Bug 数或宣传需要决定版本。仅改名称、Logo、颜色、字号、布局或新增一个余额服务，默认不升主版本。

**拿不准时按较低级别处理**：兼容的新功能默认小更新；恢复既定行为默认 Bug 修复。所有者已授权维护者把握尺度，日常分级无需反复询问；如所有者明确指定版本号，记录原因并遵从，但不覆盖既有有效发布。

## 本项目的具体例子

- 新增余额服务、任务筛选／排序、提醒选项、小组件样式：通常是小更新，如 `v3.0.0 → v3.1.0`。
- 修复余额数值不一致、进度条消失、标题遮挡、错误分页、同步失败：Bug 修复，如 `v3.0.0 → v3.0.1`。
- 恢复丢失的布局属修复；主动设计新的可选布局属小更新。涉及 UI 不自动视为大更新。
- 替换项目图标、调整品牌名称或优化局部导航：若改变实际产品，通常是小更新；只改宣传图或仓库介绍则不升版本。
- 与旧协议不兼容、必须协调迁移手机／手表与 Mac 的核心协议升级：可以是大更新，必须写明迁移方法与影响。
- 仅调整版本管理文档时，不改变 App 或 Mac 服务，不发布新版本、不增加迭代次数、不要求设备重新安装。

这些是未来判断示例，不重新判定或改写已发布 v1.0.0、v2.0.0、v3.0.0 的编号和历史分类。

## 发布前执行

1. 比较上一次有效产品发布与待发布内容，将变化分为“新增内容、Bug 修复、改进、文档与维护”。同一发布混合变化按实际最高级别判断：常规功能加修复仍为小更新，只有达到重大升级门槛才为大更新。
2. 在日志中记录更新类型、对比版本和分级理由；主版本升级额外说明重大变化及迁移要求（没有迁移要求时写明）。同一批相关改动统一发布，不因每个提交、每张图或每个修复单独发版本；紧急修复可以独立发布。
3. 有效产品发布同步 `VERSION`、README、CHANGELOG、下载索引及 Release；保留固定源码下载。项目版本与 App 构建号、Python 包版本分别管理，不自动联动。
4. 只有有效产品发布才增加一次累计迭代，文档补充不计数。版本号表达变化等级，累计迭代表示发布次数，两者不互相推算。
5. 文档变更并入当前版本的“文档与维护补充”，同步 GitHub 时说明改了什么、产品新增和 Bug 修复是否为无。不得新建产品 Release、移动已发布标签或重写历史源码包。

历史版本索引见 [CHANGELOG](../CHANGELOG.md#版本索引)，维护流程见 [长期维护计划](maintenance.md)。
